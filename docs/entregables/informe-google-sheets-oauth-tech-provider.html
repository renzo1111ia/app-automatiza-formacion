Google Sheets con una sola app y conexión de 1 clic

Modelo "Tech Provider" para Google OAuth en dashboard-af (sin que el cliente cree apps ni API keys)
Proyecto: dashboard-af — AI CRM + Workflow Orchestrator multi-tenant
Preparado para: Automatiza Formación
Fecha: 3 de junio de 2026
Ámbito: impacto técnico, arquitectónico y operativo · scope drive.file

1. El objetivo: conectar Sheets con un clic, sin fricción

El proyecto ya tiene la integración bidireccional de Google Sheets construida (lectura de filas como leads, escritura de vuelta de estados, watch en tiempo real vía Drive, mapeo de columnas). Lo que cambia aquí no es la integración: es el modelo de conexión del cliente.

Modelo actual del proyecto (BYO — "trae tu propia app")

Hoy, cada academia (cada "tenant") tiene que crear su propia aplicación en Google Cloud Console antes de poder conectar una hoja:

crear proyecto Cloud  ·  habilitar 3 APIs  ·  configurar consent screen
crear OAuth Client ID  ·  copiar Client ID + Client Secret  ·  pegarlos en el dashboard

Son 5–10 minutos de pasos técnicos en una consola que el cliente final no conoce, propensos a error (redirect URI mal puesto, API sin habilitar, test user no añadido) y generan carga de soporte. Es la principal barrera de adopción.

El modelo propuesto sustituye todo ese montaje por un único botón "Conectar con Google": el cliente inicia sesión con su cuenta de Google, autoriza el acceso solo a las hojas que él elija y empieza a trabajar. La app la pone Automatiza Formación una sola vez; el cliente trabaja con su propia cuenta de Google. Es exactamente el mismo patrón que ya recomendamos para WhatsApp con el modelo Tech Provider de Meta.
Premisa de este informe: esta investigación solo tiene sentido si el resultado es que el cliente conecta su cuenta con un solo clic y un login, sin crear apps, sin sacar API keys, sin tocar Google Cloud. Si no logramos eso, no merece la pena el cambio.

Conclusión: la app única es el modelo correcto para escalar la captación de academias. El modelo BYO no se elimina: se conserva como opción avanzada para un cliente de muy alto volumen que quiera su propia cuota de Google aislada. Lo llamamos modelo híbrido: app única por defecto (99% de clientes), BYO opcional bajo demanda.

3. Por qué con Google es MÁS sencillo que con Meta

El paralelismo con el informe de WhatsApp/Meta es directo, pero hay una diferencia clave a nuestro favor: el scope que usamos con Google (drive.file) no es "sensible". Esto evita el proceso de revisión caro y lento que sí existe en Meta y en otros scopes de Google.

Requisito de revisión Meta Tech Provider (WhatsApp) Google app única (Sheets, drive.file)
Revisión de la plataformaApp Review obligatorioNo requiere revisión de scope (scope no sensible)
Vídeos de demostración2 vídeos obligatoriosNo
Auditoría de seguridad externa—No (CASA solo aplica a scopes restringidos)
Verificación de empresa / marcaVerificación de empresa obligatoriaSolo brand verification (logo + web + privacidad): 2–3 días
Límite de clientes10 / 7 días → 200 tras verificarSin límite en producción con scope no sensible
Cuello de botellaApp Review con vídeo (días/semanas)Brand verification (2–3 días hábiles)
Corrección importante respecto a documentación interna previa: alguna guía antigua del proyecto afirmaba que "una app Google con >100 usuarios necesita verificación" y que por eso "cada tenant debe traer su propia app". Eso es cierto solo para scopes sensibles o restringidos (como Drive completo o Gmail). Con drive.file — que es no sensible — no hay límite de 100 usuarios ni revisión de scope. Esta es precisamente la razón por la que la app única es viable.

4. ¿Hay que cambiar código? Impacto por componente

La arquitectura ya soporta casi todo el modelo híbrido por diseño: las credenciales OAuth se guardan cifradas por tenant en columnas que admiten estar vacías, y el retorno de Google (callback) ya identifica al tenant por una firma segura (no por la URL de retorno). Eso significa que una sola app con una sola URL de retorno sirve a todos los clientes.

Componente actual Estado hoy ¿Cambia con la app única? Esfuerzo

Estado del wizard"¿Tiene credenciales?" mira solo las del tenantSí — debe considerar también la app global disponibleBajo
Almacenamiento de tokensCifrado por tenant (AES-256-GCM)Sin cambios — cada cliente guarda sus propios tokens igualNinguno
Variables de entornoNo hay credenciales globales de SheetsNuevas — Client ID + Secret globales de AutomatizaBajo
Resumen: la lógica sensible (cifrado de tokens, sincronización, escritura de vuelta) no se toca. El cambio es de onboarding y resolución de credenciales: pasamos de "el cliente crea una app y pega 2 secretos" a "el cliente pulsa un botón e inicia sesión". Estimación gruesa: fallback de credenciales + rediseño del wizard + variables + prueba E2E ≈ medio sprint dedicado, encajable como Sprint 11 post-MVP (no toca el MVP de HubSpot + Zoho ni el SPIKE de Sheets ya entregado).

5. Cómo queda el flujo del cliente (objetivo)

  1. El cliente entra en Ajustes → Integraciones → Google Sheets.
  2. Ve un único botón "Conectar con Google" (sin formularios de credenciales).
  3. Pulsa, inicia sesión con su cuenta de Google y ve un consentimiento con el nombre "Automatiza Formación" pidiendo acceso solo a las hojas que elija.
  4. Vuelve al dashboard ya conectado y selecciona sus hojas con el selector de Google.
  5. Empieza a trabajar: las filas se procesan como leads y los estados se escriben de vuelta.
El cliente nunca ve la consola de Google Cloud, nunca genera una API key y nunca copia un Client Secret. Justo lo que se pide. El modo BYO (crear su propia app) queda escondido como "¿Necesitas tu propia cuota de Google? Usa tu propia app" para el cliente avanzado que lo solicite.

7. Riesgos y mitigaciones

RiesgoMitigación
Cuota compartida de Google API entre todos los clientesSuficiente para el volumen previsto. Para un cliente de alto volumen, se ofrece el modo BYO (su propia app = su propia cuota). Se puede solicitar ampliación de cuota a Google si hace falta.
Clientes con Google Workspace corporativo restrictivo que bloquean apps de tercerosCaso minoritario. Para ellos, el modo BYO o una autorización del administrador de Workspace lo resuelve.
Aviso "app no verificada" mientras no se complete brand verificationIniciar brand verification cuanto antes (2–3 días). Mientras tanto, el aviso no impide conectar.
Exposición del Client Secret globalSe cifra y se guarda fuera del repositorio (solo en variables de entorno del servidor y vault). Nunca en git, docs ni capturas.

8. Recomendaciones

  1. Adoptar el modelo de app única como conexión por defecto. Es lo que convierte la integración en un producto comercializable: el cliente conecta en segundos.
  2. Conservar BYO como opción avanzada. Nadie paga la cuota que no necesita: app global para el 99%, BYO para alto volumen.
  3. Pasar la app a producción + iniciar brand verification pronto. Resolver primero, porque elimina la caducidad de tokens a 7 días (un dolor ya conocido) y la espera de Google es el único tiempo muerto.
  4. Encajar como Sprint 11 post-MVP dedicado. No toca el MVP (HubSpot + Zoho) ni el SPIKE de Sheets ya entregado.
  5. Acción inmediata de la clienta: crear el proyecto Google Cloud de Automatiza, habilitar las 3 APIs y crear el OAuth Client ID (pasos guiados al final de este informe).

9. Guía paso a paso — montar la app única (Automatiza)

Esta guía es para Automatiza Formación, se hace una sola vez. Al terminar, los clientes ya no tienen que crear nada: solo pulsan "Conectar con Google". Todos los enlaces abren en pestaña nueva.

Paso 1 · Crear el proyecto en Google Cloud

Inicia sesión con la cuenta de Google de Automatiza Formación y crea un proyecto nuevo (por ejemplo automatiza-dashboard-prod).

🔗 console.cloud.google.com/projectcreate

Paso 2 · Habilitar las 3 APIs necesarias

En la biblioteca de APIs, busca y pulsa Enable en cada una: Google Sheets API, Google Drive API y Google Picker API.

🔗 Sheets API · Drive API · Picker API

Paso 3 · Verificar el dominio en Google Search Console

Necesario para poder publicar la app. Añade el dominio (automatizaformacion.com) y verifícalo con un registro DNS TXT o subiendo un archivo HTML.

🔗 search.google.com/search-console

Paso 4 · Configurar la pantalla de consentimiento (OAuth consent screen)

Tipo External. Rellena: nombre de la app ("Automatiza Formación"), email de soporte, logo, página de inicio y política de privacidad (URLs públicas HTTPS). Añade los scopes .../auth/drive.file y .../auth/userinfo.email.

🔗 console.cloud.google.com/apis/credentials/consent

Paso 5 · Crear el OAuth Client ID (Web application)

En Credentials → Create credentials → OAuth client ID, tipo Web application. En Authorized redirect URIs añade la URL de retorno de producción:

https://app.automatizaformacion.com/api/integrations/google/callback

(Añade también la de dev si se va a probar ahí). Al crear, copia el Client ID y el Client Secret: son las 2 variables que necesita el equipo de desarrollo (se guardan en el servidor, nunca en git).

🔗 console.cloud.google.com/apis/credentials

Paso 6 · Pasar la app a producción

En la pantalla de consentimiento, pulsa Publish app (Publishing status → In production). Esto elimina la caducidad de tokens a 7 días. Con scope drive.file (no sensible) no se requiere revisión de scope para publicar.

🔗 console.cloud.google.com/apis/credentials/consent (botón "Publish app")

Paso 7 · Enviar la verificación de marca (brand verification) — opcional pero recomendado

Desde la misma pantalla, envía la app a brand verification (logo + página de inicio + política de privacidad). Espera de 2–3 días hábiles. Al aprobarse, desaparece el aviso "Google no ha verificado esta app" del consentimiento del cliente.

🔗 Guía oficial de verificación OAuth

Paso 8 · Entregar las 2 credenciales al equipo de desarrollo

Pasa el Client ID y el Client Secret por canal seguro (no email, no chat). El equipo los configura como variables de entorno globales en local y en el servidor del VPS. A partir de aquí, cualquier cliente conecta con un solo clic.

🔗 (interno) Variables: GOOGLE_SHEETS_CLIENT_ID · GOOGLE_SHEETS_CLIENT_SECRET

Resultado final: una sola app de Google, propiedad de Automatiza, en producción. El cliente entra, pulsa "Conectar con Google", inicia sesión y elige sus hojas. Cero apps por cliente, cero API keys, cero consola de Google Cloud para el cliente.
