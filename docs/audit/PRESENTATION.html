Verificación en navegador producción real

Auditoría manual con Playwright sobre https://app.automatizaformacion.com con cuenta real del cliente. 38 chunks JS analizados (12 sin login + 26 con sesión). Cookies, localStorage, network y HTML inline inspeccionados.

✓ NO está pasando

  • JWTs NO aparecen en ningún bundle JS público (0 hits en 38 chunks)
  • JWTs NO aparecen en HTML inline ni __NEXT_DATA__
  • JWTs NO aparecen en localStorage ni sessionStorage
  • Cookie de sesión sb-api-db-auth-token es httpOnly (correcto)
  • 0 hosts externos contactados — todo proxificado por la app (sin tráfico directo cliente↔Supabase)
  • El navegador del usuario final está, en este punto, limpio

✗ SÍ está expuesto

  • 2 JWT service_role en el repositorio GitHub (admin DB hasta 2030)
  • Fallback silencioso: si falta env var, la app usa el JWT del código sin error
  • Scripts migrate-*.ts ejecutables con credenciales hardcoded → admin DB directo bypaseando Next.js
  • Subdominio interno api-db revelado por el nombre de la cookie
  • esden-tenant-id en cookie plain editable desde DevTools (clave del Vector 1)
  • RLS basada en JWT claim tenant_id es dead letter: el claim no existe

Spec cliente vs código gap analysis

La documentación de la cliente (docs/Docs-entrega-clienta/) es autoritaria. Si el código diverge, el código está mal. Estos son los gaps confirmados.

Regla B cualificación: técnico con ≥2 años de experiencia es apto
→
Código: requiere ≥3 años (rechaza leads válidos) · qualifier.ts:80
Schema qualified: debe ser "apto" / "no apto"
→
Código: 3 schemas distintos coexistiendo (si/no, SI/NO, cualificado/no cualificado)
Variables: {user_profesion}, {years_experience}
→
Código: 4 variantes con/sin espacios + typos (YEARS_EXPERIENCIE, YEARS_ EXPERIENCIE)
Multi-tenancy: aislamiento estricto entre clientes
→
Código: cookie tampering + IDOR permite cross-tenant data destruction
Flujo multi-día: día 1 voz → día 2 WhatsApp → día 3 CRM check
→
Código: bug de firma en worker.js:58 → solo día 1 funciona, resto falla silencioso
Función book_appointment
→

Sync CRM: "agregar, no sobrescribir"
→
Código: implementación parcial — no garantiza preservación de datos previos
Storage: Supabase (la cliente lo confirmó explícitamente)
→
Código: 0 referencias a Airtable. La divergencia del PNG cliente era solo visual. Resuelta.

Lo que está bien no todo arde

El sistema tiene base sólida en varios puntos. Estos elementos están bien implementados y no requieren intervención.

🎯 Camino feliz WhatsApp

Primer contacto procesa correctamente. IA responde, mensajes llegan, historial se guarda. La integración Meta Cloud API está bien montada.

🎨 UI / Dashboard

Stack moderno y coherente: Next.js 16 App Router + React 19 + Tailwind + shadcn/ui. La estética es profesional y consistente entre páginas.

🗣️ Retell voice (caso básico)

Puente con proveedor de voz implementado. Las llamadas se inician correctamente. Falta validación de firma en webhooks (ver Vector 3).

🧠 Knowledge Base (RAG)

Búsqueda semántica integrada con vector store de Supabase. RAG funcional para que la IA cite documentación del cliente.

🏗️ Decisiones arquitectónicas

Stack correcto (Next.js + Supabase + BullMQ + LangChain). Los problemas son de implementación específica, no de diseño fundamental.

🔒 Cookie de auth httpOnly

La cookie principal de sesión Supabase está marcada httpOnly correctamente — JS del navegador no puede leerla. Punto positivo confirmado en producción.
