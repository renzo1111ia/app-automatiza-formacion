3.1 · La auditoría inicial (V1, 18-may-2026) en un párrafo

La auditoría V1 fue un análisis exhaustivo de descubrimiento sobre ~15.000 líneas de código. Cubrió 5 fases (estructura, orquestador BullMQ, stack LLM, capa de datos, seguridad/dependencias) y un deep audit complementario (DA-1 concurrencia, DA-2 auth/RLS, DA-3 security, DA-4 LLM/voz, DA-5 accesibilidad). Identificó 132 hallazgos consolidados distribuidos en 23 Critical + 24 High + 18 Medium + 7 Low (quick) más ~67 deep. Los hallazgos críticos confirmaban tres capas de vulnerabilidad reforzándose entre sí: (1) autenticación y aislamiento multi-tenant rotos estructuralmente; (2) flujo multi-día BullMQ inoperativo en producción; (3) seguridad perimetral con 7 endpoints abiertos sin auth y 0 validaciones HMAC en webhooks. La V1 produjo el findings-summary.md, el deep summary, el informe ejecutivo cliente, el stack confirmado y las 13 decisiones del Auditor R-013..R-025 en el decision log.

4.0 · Adopción post-MVP planificada: LiteLLM + Langfuse + Engram + Biome

El equipo ha decidido (28-05-2026) reforzar el stack justo después del MVP v0.3.0 GA con cuatro herramientas que cubren capas distintas: gobernanza de llamadas LLM (LiteLLM Proxy), observabilidad y evaluación LLM (Langfuse), memoria persistente del proyecto para Claude Code (Engram) y toolchain de calidad de código (Biome). El objetivo: convertir el actual logging custom de costes LLM en una plataforma de observabilidad real, blindar el multi-tenant frente a abuso de cuota, reducir consumo de tokens en el flujo de desarrollo con Claude Code y acelerar el ciclo de feedback de lint+format del repositorio.

Decisión consolidada: sustituir el plan custom in-house del actual Sprint Costes-LLM (SP-5B, v0.5.1) por una implementación basada en LiteLLM Proxy self-hosted en Dokploy + Langfuse Cloud Hobby (con migración futura a self-hosted bajo condición). Engram se evaluará como piloto separado para el flujo de desarrollo del equipo.

Cuándo: inmediatamente después del MVP. El sprint actual SP-5B ya está planificado en el RoadMap como patch v0.5.1, justo después de Google Sheets v0.5.0 (Lun 24-08-2026 → Jue 27-08-2026 según fechas actuales). La ventana de implementación se respeta; cambia el alcance interno del sprint.

Engram — memoria persistente del flujo de desarrollo

Engram es una herramienta del flujo interno de desarrollo, no del producto. Sustituye el sistema actual de auto-memoria estática de Claude Code (carga 200 líneas de MEMORY.md + ~60 ficheros .md enlazados al inicio de cada chat) por una base de conocimiento local en SQLite consultable bajo demanda mediante MCP. Beneficio directo: menos tokens consumidos al reanudar trabajo en chats nuevos, mayor continuidad de contexto entre sesiones de Javi HP y Renzo.

Modo de implementación: piloto de 1 semana en máquina de Javi HP después del MVP v0.3.0 GA. Si el ahorro de tokens medido se acerca al claim del upstream (~80-90% de reducción de contexto redundante), se documenta el setup y Renzo lo adopta a continuación.

Privacidad: Engram es 100% local SQLite, cero datos a cloud, compatible con confidencialidad cliente y RGPD del proyecto. La memoria es por máquina del dev — cada uno tiene la suya y no se comparten automáticamente.

Riesgo declarado: proyecto Engram es joven (3 meses, v1.15.x). Si se detectan breaking changes en upgrade, se mantiene en versión pineada hasta que estabilice. La capa CLAUDE.md + MEMORY.md actual se preserva como fallback.

Biome — toolchain de calidad de código (linter + formatter)

Biome es una herramienta del flujo interno de desarrollo, no del producto. Sustituye el dúo ESLint + Prettier por un único binario Rust que combina linter, formatter y organize-imports. Cobertura actual (v2.4.16, mayo 2026): ~502 reglas de lint, ~97% paridad Prettier en formato, ~85% paridad typescript-eslint en reglas type-aware. Casos reales de migración reportan reducciones de pre-commit del orden 10-25× (caso fireup.pro: 27.2s → 1.8s, 92.6% reducción).

Mejoras concretas para dashboard-af
  • Pre-commit hooks 10-25× más rápidos — el repo tiene husky + lint-staged consolidado desde Sprint 0. En repos comparables (1-3k archivos TS) el feedback baja de ~10-15s a <500ms. Con el ritmo del equipo (decenas de commits al día), el ahorro acumulado es real.
  • Una herramienta vs cinco — hoy conviven ESLint + Prettier + eslint-plugin-prettier + @typescript-eslint + plugins. Biome consolida todo en un binario con un único biome.json de configuración.
  • Type-aware sin tsc — reglas tipo noFloatingPromises ejecutan inferencia propia sin necesidad de compilar el proyecto completo (relevante para el código async-heavy con BullMQ + LangChain + Retell/Ultravox webhooks).
  • Auto-fix categorizado seguro/inseguro — Biome marca explícitamente qué fixes son safe vs unsafe. Más limpio que el batch fixing actual de ESLint.
  • Diagnostics estilo compilador Rust — mensajes contextualizados con span del error en el código (DX superior).
  • Binario único en CI — sin node_modules necesario para lint+format si se cachea el binario; pipelines GitHub Actions más rápidos.

  2. Cobertura type-aware al 75-85% en reglas como noFloatingPromises — perder ese 15% de cobertura en código con concurrencia BullMQ + LangChain + multi-LLM es regresión real de seguridad durante el MVP.
  3. Tailwind sort en nursery con fix unsafe — la UI del dashboard es Tailwind-heavy; no es momento de exponerse a fix automáticos potencialmente peligrosos.
  4. Coste de oportunidad alto en MVP — la migración cuesta ~13-17h nominales (~5-8h al ritmo del equipo), y esas horas tienen mejor retorno cerrando funcionalidad de cara a la clienta que cambiando toolchain interno.

Cuándo SÍ migrar: después de cerrar SP-4-LINT-ZERO (baseline en 0 con ESLint) y después del MVP v0.3.0 GA. Ventana sugerida: tras el sprint Refinamiento Herramientas (v0.5.2) o como sprint dedicado posterior, condicionado a:

  • useSortedClasses sale de nursery con fix safe estable, o
  • noFloatingPromises alcanza ≥95% paridad con typescript-eslint, o
  • aparece un biome-plugin-next oficial cubriendo las reglas Next.js que hoy faltan.

Mientras tanto, mejora incremental sin riesgo (1-3h, recomendada YA): migrar el .eslintrc legacy del proyecto a eslint.config.js flat config + activar caché ESLint (--cache) en husky. Da 5-10× de velocidad en runs incrementales sin cambiar de herramienta. Cero coste de baseline, cero riesgo.

4.4 · ¿Qué NO externalizar?

El Auditor recomienda mantener auto-hospedado el core (Postgres, PostgREST, GoTrue, Storage, Redis, BullMQ, Sentry/GlitchTip). Las razones: control de datos del cliente, pricing predictible, evitar lock-in. La complejidad operativa adicional se compensa con el ahorro y la propiedad de los datos.

Sí externalizar: Anthropic/OpenAI/Gemini (proveedores LLM — no replicables), Retell/Ultravox (voz outbound — proveedores especializados), WhatsApp Cloud API (Meta, monopolio).

📌 Nota sobre privacidad de la inferencia LLM (variante privativa): si la clienta o un tenant final exige que los datos de la conversación NO salgan de su nube (caso típico en formación regulada, sanidad, banca), los tres LLM se pueden consumir en modo "privativo" alojando la inferencia en hyperscaler con SLA empresarial:

  • Anthropic Claude → AWS Bedrock · Azure AI Foundry · Google Vertex AI. Misma API, los prompts/respuestas no salen del cloud contratado, BAAs disponibles.
  • OpenAI GPT → Azure OpenAI Service (sigue siendo OpenAI pero con SLA Azure + residencia de datos EU/US a elegir + sin uso para entrenamiento).
  • Google Gemini → Vertex AI nativo (Gemini Pro/Flash dentro de Google Cloud, datos no usados para entrenamiento por defecto).

Implicación: usar la variante privativa de un LLM cuesta ~15-30% más por token que el API pública del proveedor, pero entrega cumplimiento contractual con clientes corporativos. La decisión arquitectónica (qué provider y en qué cloud) es la misma que la del programa cloud que se acepte (Bloque 4 Fase 3.bis): si se acoge Microsoft for Startups → usar Azure OpenAI y Azure AI Foundry; AWS Activate → Bedrock; Google for Startups → Vertex.

8.4 · Por qué las estimaciones realistas son tan bajas

Los Sprints 0/1/2/2B han cerrado con un ratio −91% a −94% sobre las estimaciones iniciales. Las razones (validadas en sesión 24-may con Javi HP):

  • Orquestación multi-agente Claude Code: tareas paralelas con subagentes especializados (database, security, frontend-developer, tester, code-reviewer) en lugar de secuencial.
  • Arquitectura de contexto madura: skills + memorias persistentes + reports estructurados que evitan reexplicar contexto.
  • ADRs documentados: las decisiones arquitectónicas no se revisan, solo se ejecutan.
  • Tracking riguroso: el RoadMap.md detecta y corta scope creep en cuanto aparece.
  • Local-first: validación E2C local antes de E2E VPS evita ciclos largos de despliegue.

Las estimaciones realistas asumen mantenimiento de este patrón. Si el equipo se amplía con devs no-orquestados, los ratios subirán (estimar 50% del original como peor caso).
