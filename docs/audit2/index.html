3.1 · La auditoría inicial (V1, 18-may-2026) en un párrafo

La auditoría V1 fue un análisis exhaustivo de descubrimiento sobre ~15.000 líneas de código. Cubrió 5 fases (estructura, orquestador BullMQ, stack LLM, capa de datos, seguridad/dependencias) y un deep audit complementario (DA-1 concurrencia, DA-2 auth/RLS, DA-3 security, DA-4 LLM/voz, DA-5 accesibilidad). Identificó 132 hallazgos consolidados distribuidos en 23 Critical + 24 High + 18 Medium + 7 Low (quick) más ~67 deep. Los hallazgos críticos confirmaban tres capas de vulnerabilidad reforzándose entre sí: (1) autenticación y aislamiento multi-tenant rotos estructuralmente; (2) flujo multi-día BullMQ inoperativo en producción; (3) seguridad perimetral con 7 endpoints abiertos sin auth y 0 validaciones HMAC en webhooks. La V1 produjo el findings-summary.md, el deep summary, el informe ejecutivo cliente, el stack confirmado y las 13 decisiones del Auditor R-013..R-025 en el decision log.

BLOQUE 4

Puntos críticos de escalado y recomendaciones de cara al crecimiento

Qué servicios saturarán primero, dónde estarán los costes y qué externalizar (o NO).

4.1 · Supabase self-hosted (Dokploy en Hetzner) — el core

Riesgo: el VPS actual ejecuta en un único nodo el Postgres + Kong + PostgREST + GoTrue + Storage + Next.js + BullMQ workers + Redis. Toda la pila compite por los mismos cores/RAM/disco.

Carga proyectada al cierre del MVP: 5-10 tenants × 100-500 leads/día × N agentes IA conversacionales × M webhooks Retell/WhatsApp/CRM. Tráfico burst en horas pico (10:00 ES, 18:00 ES).

Sub-riesgos concretos

ServicioPunto saturaciónSíntoma esperadoRecomendación
Postgres~200-500 conexiones simultáneas (pool por defecto 100)Latencias >500ms, errores too many connectionsActivar PgBouncer en transaction mode. Sprint pre-deploy.
PostgRESTCPU-bound en queries complejasTimeouts en endpoints REST de SupabaseCache de respuestas idempotentes + uso preferente del SDK desde server (no REST directo).
GoTrue (auth)Login bursts (mañanas)JWT issuance lento, registros fallidosFront rate-limiting + monitorización.
BullMQ + RedisBacklog si workers no escalanLeads esperando outbound >30minWorkers en proceso separado (no embebidos en Next.js). Métricas Bull-Board ya planificadas Sprint 3.
Next.js + ORM-lite (Repository)N+1 si crece dataset por tenantPágina tarda >2s en cargar listas largasPagination obligatoria + indexes Postgres + revisión queries Sprint 3.
Storage SupabaseDisco VPS limitadoCierre de uploads, errores 507Plan migración a S3 self-hosted (MinIO) o S3 AWS managed cuando >50 GB.

Recomendación estratégica (Auditor)

Fase 1 (pre-MVP, opcional): mantener single-node, activar PgBouncer, instrumentar métricas (Sentry Performance + logs Pino agregados).

Fase 2 (post-MVP, primeros 50-100 leads/día reales): separar Postgres a su propio nodo (read-replica para queries pesadas), workers BullMQ a su propio nodo, Next.js a un tercer nodo. Hetzner permite VPS dedicados con red privada gratuita.

Fase 3 (escala >500 leads/día): Postgres con réplica + connection pooling externo. Considerar mover storage a S3 managed. Mantener el stack auto-hospedado salvo storage.

NO recomendado por el Auditor: migrar a Supabase Cloud managed pagado — pierdes control, depende de su pricing y de su roadmap (lo que ya descartó Sprint 0 cuando se cerró R-023).

4.2 · Sentry — limitación plan Free 5k events/mes

Estado actual: Sentry validado en VPS 26-may con plan Developer Free (5.000 events/mes, retención 30 días, 1 usuario).

Riesgo: en producción multi-tenant los 5k/mes se agotan en horas. Un solo bucle JS no-capturado en frontend puede generar 200-500 events/min. Un cron que falla en bucle = noche perdida + alertas off.

Opciones

OpciónCosteProsContras
Sentry Team plan (gestionado)~26 USD/mes (50k events)Sin mantenimiento. Alerting + integraciones.Escala lineal con eventos. 100k = 80 USD, 250k = 200 USD/mes. Coste creciente con escala.
Sentry self-hosted (Docker)VPS dedicado (~10-20 USD/mes Hetzner)Coste plano. Sin límite de events. Datos propios.Requiere mantenimiento (upgrades, BD, storage). Stack pesado (Kafka, ClickHouse, Postgres).
Alternativa: GlitchTip (open-source)Self-host barato (~5 USD/mes)Compatible con SDK de Sentry. Stack ligero.Menos features que Sentry. Comunidad menor.
Alternativa: logs estructurados Pino + Loki/GrafanaVPS pequeñoCoste plano. Control total.No reemplaza tracking de errores con stacktrace + breadcrumbs.

Recomendación Auditor: NO externalizar Sentry pagado en cuanto haya tráfico real. Migrar a Sentry self-hosted en VPS dedicado (mismo Hetzner) o GlitchTip si se prioriza simplicidad. Mantener el plan Free actual SOLO durante MVP / pre-deploy de validación.

4.4 · ¿Qué NO externalizar?

El Auditor recomienda mantener auto-hospedado el core (Postgres, PostgREST, GoTrue, Storage, Redis, BullMQ, Sentry/GlitchTip). Las razones: control de datos del cliente, pricing predictible, evitar lock-in. La complejidad operativa adicional se compensa con el ahorro y la propiedad de los datos.

Sí externalizar: Anthropic/OpenAI/Gemini (proveedores LLM — no replicables), Retell/Ultravox (voz outbound — proveedores especializados), WhatsApp Cloud API (Meta, monopolio).

BLOQUE 7

Test /e2etotal — sistema E2E exhaustivo

Test maestro de regresión total reusable, ejecutado al cierre de la auditoría V2.

7.1 · Qué es /e2etotal

/e2etotal es un comando custom del proyecto que ejecuta una batería E2E exhaustiva sobre todo el sistema. No es un test puntual: es un audit completo reusable que incluye:

  • Smoke tests sobre todas las rutas públicas y autenticadas.
  • Tests funcionales de flujos críticos: login, gestión de leads, integraciones CRM, OAuth, configuración tenant.
  • Validación WCAG 2.2 AA con axe-core sobre las páginas principales.
  • Validación de rendimiento básico (Core Web Vitals locales).
  • Inspección de network: detección de requests fallidos, latencias anómalas, errores en consola.
  • Documentación automática del resultado en docs/e2e-runs-history.md con histórico de ejecuciones.

7.2 · Comando y parámetros

/e2etotal                          # ejecución completa con defaults
/e2etotal --quick                  # solo smoke tests
/e2etotal --area=leads             # solo área leads
/e2etotal --area=crm               # solo integraciones CRM
/e2etotal --vps                    # contra VPS en lugar de localhost
/e2etotal --skip-wcag              # omitir axe-core
/e2etotal --report=html            # exportar HTML resumen

Plan maestro: docs/e2e-full-test-plan.md. Histórico de ejecuciones: docs/e2e-runs-history.md.

8.4 · Por qué las estimaciones realistas son tan bajas

Los Sprints 0/1/2/2B han cerrado con un ratio −91% a −94% sobre las estimaciones iniciales. Las razones (validadas en sesión 24-may con Javi HP):

  • Orquestación multi-agente Claude Code: tareas paralelas con subagentes especializados (database, security, frontend-developer, tester, code-reviewer) en lugar de secuencial.
  • Arquitectura de contexto madura: skills + memorias persistentes + reports estructurados que evitan reexplicar contexto.
  • ADRs documentados: las decisiones arquitectónicas no se revisan, solo se ejecutan.
  • Tracking riguroso: el RoadMap.md detecta y corta scope creep en cuanto aparece.
  • Local-first: validación E2C local antes de E2E VPS evita ciclos largos de despliegue.

Las estimaciones realistas asumen mantenimiento de este patrón. Si el equipo se amplía con devs no-orquestados, los ratios subirán (estimar 50% del original como peor caso).
